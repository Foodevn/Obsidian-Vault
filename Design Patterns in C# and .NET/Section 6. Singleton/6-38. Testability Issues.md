## Kiểm tra tính Singleton và vấn đề kiểm thử (Testability)

### Mục tiêu
- Xác minh rằng mẫu thiết kế Singleton đảm bảo chỉ có một thể hiện (instance) được tạo ra.
- Xem xét vấn đề kiểm thử (testability) khi sử dụng Singleton, đặc biệt là sự phụ thuộc vào cơ sở dữ liệu trực tiếp (live database).

### Khái niệm
- **Singleton**: Một mẫu thiết kế đảm bảo rằng một lớp chỉ có một thể hiện duy nhất và cung cấp điểm truy cập toàn cục (global access point) tới thể hiện đó.
- **Vấn đề kiểm thử**: Việc sử dụng Singleton có thể gây khó khăn trong việc kiểm thử vì mã nguồn thường phụ thuộc trực tiếp vào thể hiện Singleton, khiến việc thay thế (mocking) hoặc giả lập (faking) dữ liệu trở nên phức tạp.

### Kiểm thử tính Singleton

#### Mô tả
- Viết một bài kiểm thử (test) để đảm bảo rằng:
  - Chỉ có một thể hiện của lớp Singleton được tạo ra.
  - Các tham chiếu đến Singleton đều trỏ đến cùng một đối tượng.
  - Đếm số lần khởi tạo (instantiation) để xác minh chỉ có một thể hiện.

#### Mã nguồn kiểm thử
```csharp
[TestFixture]
public class SingletonTests
{
    private static int instanceCount = 0;
    public static int Count => instanceCount;

    public SingletonTests()
    {
        instanceCount++;
    }

    [Test]
    public void IsSingletonTest()
    {
        var db = SingletonDatabase.Instance;
        var db2 = SingletonDatabase.Instance;

        Assert.IsTrue(ReferenceEquals(db, db2)); // Kiểm tra tính tham chiếu giống nhau
        Assert.AreEqual(1, SingletonDatabase.Count); // Kiểm tra chỉ có 1 thể hiện
    }
}
```

#### Giải thích
- **Tạo hai thể hiện**: `db` và `db2` được lấy từ `SingletonDatabase.Instance`.
- **Kiểm tra tham chiếu**: Sử dụng `Assert.IsTrue(ReferenceEquals(db, db2))` để đảm bảo `db` và `db2` trỏ đến cùng một đối tượng.
- **Đếm số lần khởi tạo**: Biến tĩnh `instanceCount` được tăng trong constructor để theo dõi số lần khởi tạo. Kiểm tra rằng `SingletonDatabase.Count == 1`.

#### Vấn đề gặp phải
- Khi chạy kiểm thử, có thể xảy ra lỗi do đường dẫn tệp `capitals.txt` không chính xác khi thực thi trong môi trường kiểm thử (ví dụ: ReSharper).
- **Giải pháp**: Sử dụng đường dẫn động để truy cập tệp:
  ```csharp
  string path = Path.Combine(Path.GetDirectoryName(Assembly.GetExecutingAssembly().Location), "capitals.txt");
  ```

### Kiểm thử thành phần sử dụng Singleton

#### Mô tả
- Tạo một lớp `SingletonRecordFinder` sử dụng Singleton để tính tổng dân số (total population) của một danh sách các thành phố.
- Viết kiểm thử để xác minh tính đúng đắn của `SingletonRecordFinder`.

#### Mã nguồn lớp SingletonRecordFinder
```csharp
public class SingletonRecordFinder
{
    public int GetTotalPopulation(IEnumerable<string> names)
    {
        int result = 0;
        foreach (var name in names)
        {
            result += SingletonDatabase.Instance.GetPopulation(name);
        }
        return result;
    }
}
```

#### Mã nguồn kiểm thử
```csharp
[Test]
public void SingletonTotalPopulationTest()
{
    var rf = new SingletonRecordFinder();
    var names = new[] { "Seoul", "Mexico City" };
    int tp = rf.GetTotalPopulation(names);
    Assert.AreEqual(17500000 + 17400000, tp); // Tổng dân số kỳ vọng
}
```

#### Giải thích
- **Danh sách thành phố**: Sử dụng mảng `names` chứa `"Seoul"` và `"Mexico City"`.
- **Tổng dân số**: Gọi `GetTotalPopulation` để tính tổng dân số và so sánh với giá trị kỳ vọng (17.5M + 17.4M = 34.9M).
- **Vấn đề**:
  - Kiểm thử phụ thuộc vào cơ sở dữ liệu trực tiếp (`capitals.txt`). Nếu dữ liệu trong tệp thay đổi (ví dụ: xóa `"Mexico City"`), kiểm thử sẽ thất bại.
  - Cần tra cứu thủ công giá trị dân số từ tệp `capitals.txt`, làm tăng nguy cơ sai sót.

### Vấn đề của Singleton trong kiểm thử

- **Phụ thuộc cứng (hard-coded dependency)**:
  - `SingletonRecordFinder` gọi trực tiếp `SingletonDatabase.Instance`, khiến không thể thay thế cơ sở dữ liệu bằng một giả lập (mock) hoặc giả (fake).
  - Điều này gây khó khăn trong việc kiểm thử độc lập (isolated testing).
- **Hiệu suất**: Truy cập cơ sở dữ liệu trực tiếp tốn tài nguyên, đặc biệt khi chạy nhiều bài kiểm thử.
- **Bảo trì**: Nếu cơ sở dữ liệu thay đổi, các bài kiểm thử phải được cập nhật thủ công.

### Gợi ý cải thiện
- Sử dụng **Dependency Injection (DI)** để thay thế tham chiếu cứng `SingletonDatabase.Instance` bằng một giao diện (interface) như `IDatabase`. Điều này cho phép:
  - Thay thế cơ sở dữ liệu thật bằng một giả lập trong kiểm thử.
  - Giảm phụ thuộc vào dữ liệu trực tiếp.
- Liên kết: [[Dependency Injection]], [[Mocking trong kiểm thử]]

### Ghi chú thêm
- Công cụ sử dụng: **NUnit** để viết kiểm thử, **Autofac** để hỗ trợ DI (sẽ được đề cập trong bài tiếp theo).
- Tệp dữ liệu: Đảm bảo đường dẫn tệp `capitals.txt` được xử lý động để tránh lỗi trong môi trường kiểm thử.
- Vấn đề bảo trì: Cần xem xét cách quản lý dữ liệu kiểm thử (test data) để không phụ thuộc vào tệp ngoài.
